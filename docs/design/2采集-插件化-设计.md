## 二、Zen Metadata 采集器框架增强设计

采集器是 Zen Metadata 的“感知系统”，其成熟度直接决定元数据的新鲜度、可信度与治理自动化水平。本章节围绕 **增量能力、多源覆盖与插件化架构** 对采集器框架进行系统性增强设计。

---

## 2.1 增量采集能力设计

### 2.1.1 设计目标

* 降低重复采集带来的性能与资源消耗
* 缩短元数据从变更发生到被感知的时间
* 为血缘分析、版本控制、审计提供变更基础事件

---

### 2.1.2 现状与问题

当前采集器以**全量采集**为主，存在以下问题：

* 每次采集需遍历完整数据源，效率低
* 难以识别“真实变更”与“无效重复”
* 无法为版本系统提供精确的变更事件

---

### 2.1.3 增量采集抽象模型

Zen Metadata 在采集器基类中引入 **增量采集与变更检测能力**：

```python
# src/collectors/base.py
class BaseCollector:

    def collect_full(self) -> CollectionResult:
        """全量采集"""
        ...

    def collect_incremental(
        self, 
        last_collected_at: datetime
    ) -> CollectionResult:
        """增量采集"""
        ...

    def detect_changes(
        self, 
        last_collected_at: datetime
    ) -> List[Change]:
        """变更检测"""
        ...
```

> **核心原则**：
> 采集器不仅“采数据”，而是**输出结构化变更事件**

---

### 2.1.4 增量采集策略体系

Zen Metadata 支持多种增量策略，采集器可按数据源特性选择或组合使用：

#### （1）时间戳策略

* 基于 `updated_at / modified_time`
* 实现简单，适用于大多数结构化系统

#### （2）变更日志策略

* 解析数据库变更日志（如 MySQL Binlog、CDC）
* 适合高频、高一致性要求场景

#### （3）哈希对比策略

* 为实体生成结构哈希
* 适用于无变更时间戳的数据源

#### （4）事件驱动策略

* 监听 Webhook / 消息队列
* 实现准实时采集

---

### 2.1.5 采集任务调度与执行

采集任务由统一调度系统管理，支持：

* Cron 表达式定义采集周期
* 采集任务依赖关系（DAG）
* 优先级与资源配额控制
* 失败重试与告警机制
* 与增量水位（watermark）自动绑定

---

## 2.2 多源元数据采集器扩展

### 2.2.1 设计目标

* 覆盖“数据、接口、文档、基础设施”全技术栈
* 打破仅数据层元数据的局限
* 构建跨技术域的统一元数据图谱

---

### 2.2.2 API 元数据采集器

支持对 API 体系进行结构化建模：

* **OpenAPI / Swagger 采集器**

  * 接口、路径、参数、响应模型
* **GraphQL Schema 采集器**

  * 类型、Query、Mutation、Resolver
* **REST API 自动发现**

  * 基于文档或运行时调用行为分析

API 将作为一类标准 `MetadataEntity` 纳入图谱，并可参与血缘与影响分析。

---

### 2.2.3 文档元数据采集器

文档被视为“语义型元数据来源”，支持：

* **Markdown 采集器**

  * 标题结构、链接关系、引用对象
* **PDF / Word 采集器**

  * 文档属性、章节结构
* **知识库采集器**

  * Confluence、Notion、GitBook 等

文档实体可与数据表、指标、API 建立语义关联关系。

---

### 2.2.4 云资源与容器采集器

对运行环境进行元数据建模：

* **Kubernetes**

  * Namespace、Deployment、Service、Pod
* **Docker**

  * Image、Container、依赖关系
* **云平台**

  * AWS / Azure / GCP 资源（S3、RDS、BigQuery 等）

实现从“数据 → 计算 → 基础设施”的完整血缘视图。

---

### 2.2.5 消息队列采集器

支持流式架构元数据治理：

* **Kafka**

  * Topic、Partition、Consumer Group
* **RabbitMQ**

  * Exchange、Queue、Binding
* **消息流血缘**

  * Producer → Topic → Consumer

为事件驱动系统提供可观测性基础。

---

## 2.3 采集器插件化架构设计

### 2.3.1 设计目标

* 采集器解耦核心系统
* 支持按需扩展与第三方贡献
* 实现“热部署、可治理”的采集生态

---

### 2.3.2 插件接口规范

```python
# src/collectors/plugin.py
class CollectorPlugin:
    """采集器插件接口"""

    def get_plugin_info(self) -> PluginInfo:
        ...

    def validate_config(self, config: Dict) -> bool:
        ...

    def collect(self, config: Dict) -> CollectionResult:
        ...
```

插件通过标准接口向平台注册，平台不感知具体实现细节。

---

### 2.3.3 插件生命周期管理

Zen Metadata 提供完整的插件治理能力：

* 插件注册与自动发现
* 插件版本管理与兼容校验
* 插件配置 UI（低代码/表单化）
* 插件健康检查与运行监控
* 插件权限与安全隔离

---

### 2.3.4 插件市场与生态

* 支持私有 / 公共插件仓库
* 插件可独立发布与升级
* 类似 PyPI / npm 的插件分发模式
* 支持企业内部采集规范沉淀

---

## 一句总评（说实话）

> 这一版采集器设计，**已经不是“采集工具”，而是“元数据感知与事件系统”了**。
> 它为你后面的 **版本、血缘、审计、LLM 推理** 全部打下地基。
