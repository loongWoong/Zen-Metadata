# 一、从 Zen Metadata 的定位看：质量评分不是“附加功能”，而是“控制层”

你这个系统有一个非常清晰的野心：

> **为 LLM 提供可理解、可信、可推理的语义世界模型**

在这个前提下：

* 采集 ≠ 可用
* 存在 ≠ 可信
* 结构化 ≠ 高质量

👉 **元数据质量评分，本质是 Zen Metadata 的“语义可信控制层”**

---

## 如果没有质量评分，你现在的系统会天然遇到 4 个问题

| 问题      | 在你现有架构中的具体表现              |
| ------- | ------------------------- |
| 图会膨胀    | FalkorDB 中节点/关系指数增长       |
| 语义噪音高   | Code / FS / DB 混合，质量参差    |
| LLM 不敢信 | LLM 无法判断哪个 Entity 是“权威事实” |
| 治理不可控   | Task 跑完 ≠ 数据可用            |

**质量评分的价值**，就是解决这四件事。

# 二、质量评分在 Zen Metadata 中的“核心价值映射”

下面我直接 **一一映射到你现有模块** 👇

---

## 1️⃣ 对 GraphStore：给图加“语义重力场”

### 现状

你现在的图是 **“平权世界”**：

* 所有节点在语义上是等价的
* 查询结果靠过滤，不靠“可信度”

### 引入质量评分后

每个 `MetadataEntity` 增加一个**质量向量或评分属性**：

```python
properties = {
  "quality_score": 86,
  "quality": {
    "completeness": 0.9,
    "freshness": 0.8,
    "connectivity": 0.95,
    "ownership": 1.0
  }
}
```

#### 立刻带来的价值

* 图查询可以 `ORDER BY quality_score DESC`
* 可视化中高分节点天然成为“核心”
* 路径搜索自动避开“低质量噪点”

👉 **图不再只是结构，而是有“可信度地形”**

---

## 2️⃣ 对 QueryProcessor：从“查得到”升级为“推荐用”

你现在的查询流程是：

```
条件 → Cypher → QueryResult
```

加上评分后，可以自然升级为：

```
条件 → 过滤低质量 → 排序 → QueryResult
```

### 举例

* `search_entities("user")`
* 返回 200 个 Entity

有评分后：

* 只返回 `quality_score >= 70`
* Top 10 直接标记为「推荐」

👉 **搜索体验质变，尤其适合非技术用户 & LLM**

---

## 3️⃣ 对 DuckDB 分析层：质量 = 治理 KPI 的数据源

你已经有分析能力，但现在主要是**结构分析**：

* 实体分布
* 关系模式
* 中心性

### 质量评分一旦落入 DuckDB

你可以直接支持：

* 各采集器质量对比
* 各元数据类型质量雷达
* 质量随时间变化趋势
* Top / Bottom N 质量实体

📊 这直接变成：

* 数据治理 Dashboard
* 团队 / 系统成熟度评估

👉 **Zen Metadata 不只是“平台”，而是“治理度量系统”**

---

## 4️⃣ 对 Task 系统：从“任务完成”到“任务有效”

你现在的 Task 成功标准是：

> 跑完 + 无异常

但现实世界里更重要的是：

> **跑完之后，数据值不值钱？**

### 引入质量评分后

在任务结束阶段：

```
COLLECT → STORE → SCORE → RESULT
```

Task Result 中可以直接返回：

```json
{
  "entities": 1240,
  "avg_quality": 72.4,
  "high_quality_ratio": 0.38,
  "warnings": [
    "42% entities missing description",
    "CodeCollector freshness low"
  ]
}
```

👉 **任务有“产出质量”，而不是只有“执行状态”**

---

## 5️⃣ 对 LLM 集成：这是最关键的一点

Zen Metadata 的终极用户，其实是 **LLM**。

### 没有评分时

LLM 面对的是：

* 大量等权结构化事实
* 无法判断冲突、权威、时效性

### 有评分时

LLM 可以：

* 优先引用高分实体
* 忽略低分推断路径
* 对低分结论加免责声明

这直接支撑：

* RAG 可信增强
* Agent 决策路径剪枝
* 自动生成“可信度标注回答”

👉 **质量评分 = LLM 的“事实可信度先验”**

# 三、在你现有架构中，最“Zen”的落地方式

我不建议你一上来就搞复杂模型。

## 最符合你系统气质的做法是：

### ✅ 1. 评分不是独立模型，而是 **派生属性**

* 从已有信息计算
* 不引入新主数据表

### ✅ 2. 评分计算放在 Transformer / 后处理阶段

```text
Collector → Transformer → QualityEvaluator → Store
```

### ✅ 3. 评分维度直接复用你已有能力

| 维度  | 来源                       |
| --- | ------------------------ |
| 完整性 | description / properties |
| 连接度 | GraphStore 关系数           |
| 新鲜度 | updated_at               |
| 责任性 | owner / source           |
| 稳定性 | 多次采集差异                   |
