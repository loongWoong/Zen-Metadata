# 《Zen Metadata 血缘与影响分析设计》

## 1. 设计目标

血缘与影响分析是 Zen Metadata 从“结构化元数据管理”迈向“可决策语义平台”的关键能力，目标包括：

* 构建**多层级、跨系统的数据血缘视图**
* 支持**上游溯源、下游影响分析**
* 为变更评估、风险控制、LLM 推理提供可信路径
* 与现有图模型深度融合，不引入冗余存储

---

## 2. 设计原则

1. **血缘是派生语义，不是原始数据**
2. **统一图模型，不引入专用血缘表**
3. **血缘规则由元模型定义**
4. **分析结果可解释、可量化**

---

## 3. 血缘模型抽象

### 3.1 血缘的本质定义

在 Zen Metadata 中，血缘被定义为：

> **一组满足特定语义规则的有向路径集合**

这些路径由已有的 `MetadataEntity` 和 `MetadataRelationship` 组成，通过规则解释为血缘。

---

### 3.2 血缘层级模型

血缘层级并非不同模型，而是**同一图的不同视角**：

| 层级    | 实体粒度        | 示例                  |
| ----- | ----------- | ------------------- |
| 列级血缘  | Column      | column A → column B |
| 表级血缘  | Table       | table A → table B   |
| 作业级血缘 | Job / Query | job X → table B     |
| 跨系统血缘 | Namespace   | MySQL → Hive        |

通过 Entity 的 `granularity` 与 `source` 属性实现统一建模。

---

## 4. 血缘发现机制

### 4.1 血缘发现策略

Zen Metadata 支持多策略血缘发现：

1. **关系推断**

   * 基于 `DEPENDS_ON`、`REFERENCES`
   * 低成本、覆盖面广

2. **代码解析**

   * SQL AST（SELECT / INSERT / JOIN）
   * Python AST（DataFrame / SQL 调用）
   * 精确构建列级血缘

3. **作业与日志解析**

   * ETL / 调度系统日志
   * 构建 Job → Data 的转换链路

---

### 4.2 LineageTracker 设计

```python
class LineageTracker:
    """血缘追踪器"""

    def discover_lineage(self, entity_id: str) -> LineageGraph:
        ...

    def trace_upstream(self, entity_id: str, depth: int = -1) -> List[LineagePath]:

```

* 基于 FalkorDB 图遍历
* 动态构建血缘子图

---

## 5. 影响分析模型

### 5.1 影响分析类型

* **上游溯源分析**：数据来源可信性
* **下游影响分析**：变更传播范围
* **变更模拟分析**：假设性影响评估

---

### 5.2 风险量化模型

影响风险通过以下因子综合计算：

```text
ImpactRisk =
  PathLength
  × (1 / AvgQualityScore)
  × EntityTypeWeight
```

| 因子           | 说明       |
| ------------ | -------- |
| PathLength   | 血缘路径长度   |
| QualityScore | 元数据质量评分  |
| TypeWeight   | 实体类型风险权重 |

---

## 6. 血缘可视化

* 支持层级切换（列 / 表 / 作业）
* 支持路径高亮
* 支持时间维度（结合版本系统）
* 支持影响范围折叠

---

## 7. 与元模型、质量体系的协同

* 元模型定义血缘规则
* 不同实体类型拥有不同血缘解释逻辑
* 血缘路径参与质量评分与可信度评估

# 《Zen Metadata 搜索与语义检索架构》

## 1. 设计目标

构建统一的**结构搜索 + 语义搜索 + 图推荐**能力，实现：

* 快速、准确地定位元数据
* 发现潜在相关实体
* 为 LLM 提供高质量上下文候选集

---

## 2. 搜索架构总览

```text
用户查询
  ↓
意图识别 / 查询改写
  ↓
全文搜索 + 图过滤
  ↓
语义相似度计算
  ↓
质量与结构加权排序
```

---

## 3. 全文搜索层

### 3.1 索引对象

* 实体名称
* 描述
* 标签
* 类型
* 来源系统

### 3.2 排序因子

```text
FinalScore =
  TextRelevance
  + QualityScore
  + UsageScore
```

---

## 4. 语义搜索架构

### 4.1 向量化策略

* Entity 描述 → Embedding
* 关系上下文 → Embedding
* 查询语句 → Embedding

向量可存储在：

* 向量数据库
* 或作为属性存储于 FalkorDB 节点

---

### 4.2 利用 FalkorDB 线性代数能力

FalkorDB 支持在查询中执行向量运算：

```cypher
MATCH (e:Entity)
WHERE cosineSimilarity(e.embedding, $query_vector) > 0.7
RETURN e
ORDER BY e.quality_score DESC
LIMIT 10
```

优势：

* **向量计算与图遍历融合**
* 避免跨系统 Join
* 支持“语义 + 结构”联合过滤

---

## 5. 图结构推荐

### 5.1 推荐策略

* 相似邻域（相同关系模式）
* 共同上游 / 下游
* 中心性相似实体

### 5.2 综合评分模型

```text
RecommendationScore =
  α * VectorSimilarity
+ β * GraphProximity
+ γ * QualityScore
```

---

## 6. 自然语言查询（NLQ）

### 6.1 设计原则

* 意图驱动
* 模板化查询
* LLM 仅负责解释，不直接生成 Cypher

### 6.2 示例

> “这个指标影响了哪些表？”

```json
{
  "intent": "impact_analysis",
  "entity": "BusinessMetric",
  "direction": "downstream"
}
```

# 《Zen Metadata 版本与审计模型》

## 1. 设计目标

* 完整记录元数据演进历史
* 支持回溯、对比、审计
* 与血缘、质量体系联动
* 支撑合规与治理需求

---

## 2. 版本控制模型

### 2.1 设计原则

* **GraphStore 仅存当前态**
* **版本信息独立存储**
* **事件溯源优先，快照辅助**

---

### 2.2 核心对象

```python
class MetadataVersion:
    entity_id: str
    version: int
    metamodel_version: str
    snapshot: Dict
    created_at: datetime
```

---

## 3. 版本操作接口

```python
class MetadataVersionControl:
    def create_version(self, entity_id: str): ...
    def get_version(self, entity_id: str, version: int): ...
    def list_versions(self, entity_id: str): ...
    def diff_versions(self, v1: int, v2: int): ...
    def rollback(self, entity_id: str, version: int): ...
```

---

## 4. 事件溯源与审计

### 4.1 审计事件模型

* 操作类型（CREATE / UPDATE / DELETE）
* 操作人
* 变更字段
* 变更原因

### 4.2 合规与通知

* 关键实体变更通知
* 变更审批流程
* 审计报告导出

---

## 5. 与血缘的联动

* 血缘路径绑定版本号
* 支持“历史血缘回放”
* 支持按时间点做影响分析
